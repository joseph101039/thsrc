# THSRC 自動訂票系統 — 設計文件

**日期：** 2026-04-26  
**專案：** 台灣高鐵自動搶票代理系統  
**目標使用者：** 家庭 / 小團體（少數固定乘客）

---

## 1. 系統概述

建立一個網頁介面，讓使用者輸入訂票資訊後，由系統自動向台灣高鐵訂票網站（https://irs.thsrc.com.tw/IMINT/）送出訂票請求。支援立即訂票與預約指定時間搶票，並在完成後以 Email 通知使用者。

---

### 整體架構：前後端分離


## 3. Web UI 設計

### 頁面結構：多頁 + 底部導覽列

```
[首頁 / 訂票紀錄]  [乘客設定]
        ↑                ↑
    底部導覽列（2 個頁籤）
    
    右下角 FAB 按鈕（+）→ 進入新增訂票頁
```

### 頁面清單

#### 首頁（訂票紀錄）
- 列出所有歷史訂票紀錄（卡片式）
- 每張卡片顯示：出發地、目的地、日期、狀態（搶票中 / 成功 / 失敗）、嘗試次數
- 進行中的任務顯示即時狀態
- 右下角 FAB 按鈕（+）進入新增訂票

#### 新增訂票頁
表單欄位（由上至下）：

1. **乘客** — 下拉選擇已儲存的乘客資料
2. **出發站 ⇄ 到達站** — 下拉選擇 + 互換按鈕
3. **乘車日期** — 日期選擇器
4. **期望搭乘時間** — 時間選擇器（HH:MM）
5. **允許搭乘區間** — 最早時間 / 最晚時間（兩個時間選擇器）
6. **最大重試次數** — 數字輸入（預設 10 次）
7. **訂票時機** — 切換按鈕：「立即開始」/ 「預約時間」
   - 選預約時間時顯示：預約日期 + 時間（精確到分鐘）
8. **驗證碼提示** — 固定顯示警告：訂票開始時將 Email 通知手動輸入驗證碼
9. **確認送出** 按鈕

#### 乘客設定頁
- 顯示已儲存的乘客清單（卡片式）
- 每張卡片：姓名、身份類型、身分證號、Email
- 新增 / 編輯 / 刪除乘客
- 乘客身份類型：成人、學生、敬老、愛心、兒童

### RWD 要求
- 手機優先設計（mobile-first）
- 底部導覽列固定在畫面底部
- 表單欄位全寬，觸控友善

## 4. GAS Backend 設計

### API 端點（doPost dispatcher）

| action | 說明 |
|--------|------|
| `createBooking` | 新增訂票任務，寫入 Sheet，設定時間觸發器 |
| `getBookings` | 查詢訂票紀錄列表 |
| `getPassengers` | 查詢乘客資料列表 |
| `savePassenger` | 新增 / 更新乘客資料 |
| `deletePassenger` | 刪除乘客資料 |
| `submitCaptcha` | 接收使用者手動輸入的驗證碼，繼續訂票流程 |

### 訂票邏輯流程

```
時間觸發器觸發
  │
  ├─> 查詢高鐵車次（允許區間內）
  │     └─ 無可用班次 → 重試次數 +1
  │           ├─ 未達上限 → 等待後重新觸發，回到「查詢車次」步驟
  │           └─ 達到上限 → 更新 Sheet → 發送失敗 Email（原因：無可用班次）→ 結束
  ├─> 選擇最接近期望時間的班次
  ├─> 取得驗證碼圖片
  ├─> Email 通知使用者 → 等待驗證碼輸入（submitCaptcha）
  ├─> 送出訂票請求
  │     ├─ 成功 → 更新 Sheet → 發送成功 Email → 結束
  │     └─ 失敗 → 重試次數 +1
  │           ├─ 未達上限 → 回到「取得驗證碼」步驟
  │           └─ 達到上限 → 更新 Sheet → 發送失敗 Email（原因：訂票失敗）→ 結束
```

### 排程機制
- 使用 GAS `ScriptApp.newTrigger().timeBased().at(date).create()` 設定精確到分鐘的一次性觸發器
- 立即訂票：建立任務後直接執行，不設觸發器
- 預約訂票：設定觸發器，到時間才執行

### GAS 執行限制處理
- GAS 單次執行上限 6 分鐘
- 每次重試前檢查剩餘執行時間，若不足則重新建立觸發器繼續執行
- 最大重試次數由使用者設定，跨觸發器累計計算（狀態存 Sheet）

## 5. Google Sheet 結構

### Sheet 1：`bookings`（訂票任務與歷史）

| 欄位 | 說明 |
|------|------|
| id | 唯一識別碼 |
| passengerId | 乘客 ID |
| fromStation | 出發站 |
| toStation | 到達站 |
| date | 乘車日期 |
| desiredTime | 期望搭乘時間 |
| earliestTime | 允許最早時間 |
| latestTime | 允許最晚時間 |
| maxRetries | 最大重試次數 |
| scheduledAt | 預約搶票時間（null 表示立即） |
| status | `pending` / `running` / `success` / `failed` |
| retryCount | 目前已嘗試次數 |
| trainNo | 成功訂到的車次號碼 |
| ticketNo | 訂票成功後的票號 |
| createdAt | 建立時間 |
| updatedAt | 最後更新時間 |

### Sheet 2：`passengers`（乘客資料）

| 欄位 | 說明 |
|------|------|
| id | 唯一識別碼 |
| name | 姓名 |
| idNumber | 身分證字號 |
| type | `adult` / `student` / `senior` / `disabled` / `child` |
| email | 通知用 Email |

## 6. Email 通知

### 驗證碼通知
- **時機：** 訂票開始，需要使用者輸入驗證碼
- **內容：** 驗證碼圖片（或連結）+ 輸入連結（導向 Web UI 驗證碼輸入介面）

### 訂票成功通知
- **時機：** 訂票成功
- **內容：** 乘客姓名、出發地、目的地、日期、車次、票號、嘗試次數

### 訂票失敗通知
- **時機：** 達到最大重試次數仍未成功
- **內容：** 訂票資訊、嘗試次數、失敗原因

---

## 7. 驗證碼處理策略（分階段）

### 第一階段（目前實作）
1. GAS 取得驗證碼圖片（Base64 或 URL）
2. 發送 Email 通知使用者
3. 使用者在 Web UI 輸入驗證碼
4. Web UI 呼叫 `submitCaptcha` API 送回 GAS
5. GAS 繼續訂票流程

### 第二階段（未來擴充）
- 接入外部 ML OCR 解碼服務（GAS 發 HTTP 請求）
- 或自建解碼 API（Node.js + TensorFlow.js），GAS 呼叫
- 目標：全自動無需人工介入

## 10. 技術細節補充

- **CORS：** GAS Web App 設定 `Access-Control-Allow-Origin: *`，允許靜態 HTML 跨域呼叫
- **GAS doGet：** 僅用於健康檢查，所有功能透過 doPost
- **身份驗證：** 無（家庭內部使用，API 不需要登入保護）；可未來加入簡單 token
- **靜態 HTML 部署：** 本機開啟 `index.html` 即可使用，無需 web server；可選部署至 GitHub Pages
